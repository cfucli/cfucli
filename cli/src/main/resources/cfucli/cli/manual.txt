cfucli - one real shell, watched by a human, driven from here.

WHAT IT IS

  A shell runs on some machine. A window on that machine shows it. This cli talks to the same
  shell, so a command it runs appears in that window as it happens, and everything either side
  does is recorded and queryable afterwards.

  That machine can be across the internet - both ends dial outbound to an Upstash rendezvous, so
  neither needs an inbound port, a VPN or admin rights. Or it can be this machine, in which case
  nothing goes near the internet at all.

TWO WAYS TO USE IT

  1. A console on this machine.  No account, no credentials, nothing metered, sub-millisecond.

       cfucli console --node work
       cfucli exec --node work "mvn -q install"
       cfucli screen --node work

     A window opens on the shell. You drive it; the person at the keyboard watches it and can
     type into it. This is the case an agent's own built-in console handles badly: it floods the
     transcript, the human cannot see it or type into it, stdin cannot be supplied, and attaching
     to it from outside is awkward. Every one of those is answered below.

  2. A session with another machine.  The far end runs the window app and reads out two things.

       cfucli join 123456789 -p ABCD-EFGH --node far
       cfucli exec --node far "dir"

     If the id turns out to be a session hosted on THIS machine, the relay is skipped
     automatically and the loopback is used instead. Nothing to configure; status says which.

THE MODEL - four things worth knowing before you start

  A node is a resident process holding one session and its history. --node picks which one; the
  default is called "default". Any verb starts one if none is running. Two nodes cannot share a
  name, because the history store is held exclusively.

  The window IS the node. So a node started headless has no window and cannot grow one later -
  "screen" will say so honestly rather than pretend. If a human should be able to watch, start it
  with "console" (or the window app), not with "node start".

  exec is not the shared shell. It runs its own process beside the shell, which is the only way an
  exit code and separated streams can be exact - a shell sitting in a pager or at a password
  prompt cannot give you either. The transcript is echoed into the shared view so the human still
  sees what you did. When you genuinely want to drive the shell itself - change directory, answer
  a prompt, interrupt something - use send-keys.

  Anything longer than one line should go through run-script rather than exec. A command reaches
  the far shell as a STRING, so every layer between here and there gets a turn at its quotes - your
  own shell, this cli, then the interpreter over there - and a PowerShell one-liner with nested
  quotes is the most reliable way there is to waste an hour on this tool. Write the script to a
  file and hand over the file: it is put, exec and delete, the job appears in "jobs" exactly as an
  exec would, and the script exit code is the answer. When the session is on this machine nothing
  is staged at all, because there is nowhere to send it to.

  The terminal carries the shell and nothing else. What the tool itself did - a command an agent
  ran, a viewer arriving, a refusal - goes to a separate activity channel: F12 opens it as a pane
  under the terminal in the window, and it is the "control" stream in the recording. So a
  transcript you read back is the program's output, not the program's output with a log spliced
  through it, and nothing this tool says can land in the middle of what the shell was drawing.

  So if a person is going to WATCH an agent work, tell them to press F12 before you start. The
  terminal pane shows the shell, not the commands driving it: the legend counts what is waiting
  and names the key, but somebody watching the shell go by has been given the output and not the
  instructions. Where being seen matters more than an exact exit code, send-keys types into the
  visible shell instead.

  Everything is recorded locally as it happens: input, output, exec stdout, exec stderr, control
  and error, each with a sequence number. That is what makes summary, jobs, grep and events work
  without asking the far end anything.

  A shared session ends by itself. Fifteen minutes with nothing happening, or four hours whatever
  is happening - both from settings, both reported by "status" as "expires". A running job counts
  as something happening, so a long build is not cut off underneath you. A LOCAL-ONLY console is
  exempt: nothing about it is reachable off this machine, so there is no remote access to time out,
  and an agent's console may sit untouched for as long as it likes.

VERBS

  Starting and stopping
    console [--shell S] [--cwd D] [--headless] [--relay]   a shell on this machine, in a window
    host [--shell S] [--local]                             share this machine's shell, print id + password
    join <id> -p <password>                                connect to a shared session
    local                                                  sessions hosted on this machine right now
    end                                                    end the session on this node
    node start | node stop                                 the resident half, by hand

  Running things
    exec <command...>                                      run it; its exit code becomes this command's
      --cwd D  --timeout S  --stdin TEXT  --stdin-file F|-  --max-bytes N  --quiet  --detach
    wait <jobId> [--timeout S]                             pick up a detached job
    cancel <jobId>                                         kill a job that is still running
    send-keys <text...> [--no-enter] [--ctrl c]            type into the shared shell, as a person would
    run-script <file> [args...] [--shell S] [--keep]       send a local script over, run it, delete it
      -t S  --cwd D  --max-bytes N  --quiet                 the answer is the script exit code

  Moving files (from the end that joined)
    put <local> [remote] [--via R] [--force] [-t S]        send a file to the far machine
    get <remote> [local] [--via R] [--force] [-t S]        fetch one from it
                                                           a directory is allowed as the destination
                                                           routes: auto (default), relay, shared, same-machine

  Looking
    screen                                                 the screen as rendered, right now
    status [--show-password]                                what this node is doing, and whether the far end answers
    summary [--session id]                                 one page: counts, bytes per stream, failed jobs
    tail [-n N] [-f] [--for S] [--streams ...] [--raw]     the last of what it printed, optionally following
                                                           default streams: shell - output, exec stdout, exec stderr
                                                           --streams all adds the tool's own control and error lines

  History  - every one of these reads the local store, so they work long after a session ended.
            A node is started on demand if none is running, the same as anywhere else; --no-start
            refuses instead. With no live session they ask for --session and list what is on hand.
    jobs [--failed] [--exit-code N] [--session id]         every command, with exit code, bytes and duration
    job <jobId> [--session id]                             one command, with its full stdout and stderr
                                                           a job id is unique, so --session only checks it
    events [--from N] [--to N] [--streams ...] [--limit N] a slice by sequence number
    grep <regex> [--streams ...] [--context N] [-i]        search the recording
    sessions [--limit N]                                   sessions this node has recorded

  The rendezvous this machine uses
    relay show [--reveal]                                  what is configured; masked unless asked
    relay set --from <file|->                              point it at one; a file, never a flag
    relay clear [--yes]                                    forget it - this machine goes local-only

  Control (host side)
    lock [--off]                                           stop the remote end doing anything
    view-only [--off]                                      let it watch but not type

  Admin
    forget [--session id]                                  delete a recording
    scrub [--session id]                                   blank the text, keep the shape and exit codes
    retain [--days N]                                      drop recordings older than the window

EXIT CODES

  From exec and wait, the command's own exit code, unchanged. That is the point of them.
  0   the verb did what it was asked
  4   the far end refused it, or the node did - the reason is on stderr. Also a transfer that did
      not complete, including one refused for being too big for the relay
  5   nothing to talk to: no node running, or no screen to show
  70  something else went wrong, or a command's exit code could not be determined

  So "exec ... ; if ($?)" behaves exactly as it would locally, and 70 never masquerades as success.

FLOODING, STDIN, AND THE OTHER THINGS THAT USUALLY GO WRONG

  Too much output       exec cuts each stream at 200000 bytes and says on stderr what it cut and
                        which job id holds the rest. --max-bytes changes it, --max-bytes 0 turns
                        it off, --quiet prints nothing and leaves only the exit code.
  Something long        exec --detach returns a job id at once; wait picks it up later, tail -f
                        watches it meanwhile, cancel kills it.
  Needs input           --stdin "text" or --stdin-file F, and - reads this process's stdin. The
                        pipe is always closed afterwards, so a command that reads stdin and is
                        given none finishes instead of hanging.
  Needs the real shell  send-keys types into it, and --no-enter leaves the line unsent.
                        "send-keys --ctrl c" delivers the control character: at a prompt cmd.exe
                        cancels the line, but whether a program ALREADY RUNNING in there is
                        interrupted depends on its console mode - measured here, it did not stop
                        a running ping. To be sure of killing something, run it with exec
                        --detach and use cancel, which kills the process and its children.
  A file too big        put and get pick the route by size and SAY which they took. Small goes
                        through the relay as encrypted chunks; anything over
                        largeFileThresholdBytes (256K) goes through a folder both machines have
                        mounted, named by largeFileExchangeDir in settings on BOTH ends - a synced
                        Google Drive folder is what that is for. With no such folder, a big file is
                        REFUSED with both ways out rather than quietly costing a few hundred
                        metered messages; --via relay pushes it through anyway. Two ends on one
                        machine skip all of it and the far end just copies the file.
                        Nothing is overwritten without --force, and every transfer is checksummed.
  Where am I            screen, not tail. Forty lines that say where the shell actually is beats
                        every byte it has ever printed.
  Nothing happened      status distinguishes no session, session open but the far end silent, and
                        far end answering. It never collapses them into an empty result.

JSON

  --json on any verb that reports state prints the node's own answer, unchanged, which is the
  thing to parse. Human output is for reading and may be reformatted; the JSON shape will not be
  changed under you without reason.

FILES

  ~/cfucli/settings.toml   credentials, default shell, timeouts, retention,
                                          largeFileExchangeDir, largeFileThresholdBytes, appJar
  ~/cfucli/db/            one recording store per node
  ~/cfucli/run/           node ports, local session endpoints, node logs

  "relay set --from <file>" is the way to change the rendezvous, and it takes a FILE on purpose:
  a token given as a command-line argument is in the shell history and in any agent transcript of
  that shell for good. "relay show" tells you what is configured without printing it, and
  "relay clear --yes" makes a machine local-only again - which is what to run on a machine you are
  handing back or decommissioning.

  A Windows path in settings.toml goes in SINGLE quotes - largeFileExchangeDir = 'C:\some\folder'.
  In double quotes every backslash is an escape and the file will not parse, which stops every node
  on the machine from starting.

  Recordings hold whatever the shell printed, which can include a password someone typed. scrub
  blanks the text and keeps the shape; forget deletes; retain drops anything older than the window
  in settings - and a node now does that on its own every six hours, never touching the session it
  is recording. "status" reports what the last sweep did.
